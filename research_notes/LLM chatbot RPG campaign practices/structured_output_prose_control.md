# Structured output and prose control: what is proven to work (vendor guidance vs independent measurement)

Scope note on sourcing: the research sandbox blocked direct access to arxiv.org, aclanthology.org, openreview.net, huggingface.co, openai.com/platform.openai.com, ai.google.dev, docs.cloud.google.com, wikipedia.org and most practitioner blogs. Where a paper's numbers come only from search-engine snippets rather than the fetched full text, the entry is marked "(snippet-level)". Vendor claims are labelled [VENDOR]; independent measurements are labelled [INDEPENDENT]; practitioner posts [PRACTITIONER].

## KQ1. How reliable are schema-constrained outputs and tool calls, and what breaks?

### Takeaway
Grammar-constrained decoding ("structured outputs" / "strict tools") makes *syntactic* schema validity effectively guaranteed at OpenAI, Anthropic and Gemini, but only for a restricted JSON-Schema subset (no string-length/numeric bounds, `additionalProperties:false` required, limited recursion). What it does not guarantee: semantic correctness, non-truncation under `max_tokens`, refusals, and downstream reasoning quality; the independent evidence on whether constraints hurt reasoning is contested and prompt-sensitive.

### Cited Findings
- [VENDOR, OpenAI] Structured Outputs launched 6 Aug 2024; "On our evals of complex JSON schema following, the gpt-4o-2024-08-06 model with Structured Outputs scores a perfect 100%. In comparison, gpt-4-0613 scores less than 40%." The trained-only model reached 93%; the remaining gap to 100% was closed by constrained decoding (snippet-level; original page blocked) — [OpenAI, Introducing Structured Outputs in the API](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- [VENDOR, OpenAI cookbook] "Structured Outputs ... guarantees the model will always generate responses that adhere to your supplied JSON Schema"; enabled with `strict: true` on either `response_format` or function definitions; and a separate `refusal` field exists because "a refusal does not follow the schema you have supplied" — [OpenAI Cookbook, Structured_Outputs_Intro.ipynb](https://github.com/openai/openai-cookbook/blob/main/examples/Structured_Outputs_Intro.ipynb)
- [VENDOR, Anthropic] Structured outputs give three guarantees: "Always valid: No more JSON.parse() errors", "Type safe: Guaranteed field types and required fields", "Reliable: No retries needed for schema violations." Unsupported schema features: recursive schemas, complex types in enums, external `$ref`, numerical constraints (`minimum`, `maximum`, `multipleOf`), string constraints (`minLength`, `maxLength`), array constraints beyond `minItems` 0/1; `additionalProperties` must be `false`. SDK workaround: strip unsupported constraints, move them into field descriptions ("Must be at least 100"), and "Validate responses against your original schema (with all constraints)" client-side. First use of a schema adds grammar-compilation latency; compiled grammars cached 24 h; changing `output_config.format` invalidates the prompt cache; an extra system prompt is injected and billed — [Anthropic, Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- [VENDOR, Anthropic] Strict tool use: "guarantees Claude's tool inputs match your JSON Schema by constraining the model's token sampling to schema-valid outputs (grammar-constrained sampling)". Guarantees listed are only "Tool input strictly follows the input_schema" and "Tool name is always valid". Motivation example: without strict mode "Claude might provide passengers: 'two' or passengers: '2'" — [Anthropic, Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)
- [VENDOR, Anthropic] JSON outputs and strict tools are complementary: "JSON outputs control Claude's response format (what Claude says)"; "Strict tool use validates tool parameters (how Claude calls your functions)"; both can be combined in one request — [Anthropic, Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- [VENDOR, Anthropic] On Claude Opus 5.5 / Fable 5.1 / Mythos 5.1, forced tool use (`tool_choice: any|tool`) returns a 400; the documented replacement is `auto` plus strict tools, or structured outputs "when you need a response in a fixed JSON shape. Prompting still influences which tool auto picks." Also: with forced tool use "the models will not emit a natural language response or explanation before tool_use content blocks, even if explicitly asked to do so" — [Anthropic, Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [VENDOR, Anthropic] `input_examples` (schema-validated example inputs) are recommended "for tools with complex inputs, nested objects, or format-sensitive parameters"; each example costs ~20–50 tokens (simple) to ~100–200 tokens (nested). Tool descriptions are "by far the most important factor in tool performance"; aim for 3–4+ sentences — [Anthropic, Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [VENDOR, Anthropic, with thinking disabled] Claude Opus 5 "occasionally writes a tool call into its user-facing text instead of emitting a structured tool_use block" and can "emit <thinking> tags or other internal XML tags into its visible response"; mitigation is to keep thinking on, and a general instruction ("Do not include internal or system XML tags in your response") works better than naming the tags — [Anthropic, Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [VENDOR, OpenAI] GPT-4.1 guide: pass tools via the API `tools` field rather than injecting schemas into the prompt; "we observed a 2% increase in SWE-bench Verified pass rate when using API-parsed tool descriptions versus manually injecting the schemas into the system prompt" — [OpenAI Cookbook, GPT-4.1 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt4-1_prompting_guide.ipynb)
- [INDEPENDENT] JSONSchemaBench (EPFL/Guidance, Jan 2025): ~10,000 real-world JSON schemas (9,558 across 10 datasets incl. GlaiveAI-2K function-call schemas, GitHub Trivial→Ultra, Kubernetes, Snowplow, Washington Post, JSONSchemaStore) benchmarking constrained-decoding engines on "efficiency (speed), coverage (support for JSON Schema features), and quality (effects on underlying task accuracy)"; also usable to measure a model's *native* schema compliance without constrained decoding; now in EleutherAI lm-evaluation-harness — [guidance-ai/jsonschemabench README](https://github.com/guidance-ai/jsonschemabench); paper [arXiv 2501.10868](https://arxiv.org/abs/2501.10868) (full text blocked; snippet-level: "the best-performing constrained decoding framework supports roughly twice as many schemas as the worst-performing one")
- [INDEPENDENT] "Let Me Speak Freely?" (Tam et al., EMNLP 2024 Industry): tested three format-restriction methods (constrained decoding/JSON-mode, format-restricting instructions, NL-to-Format two stage) on 5 LLMs x 9 prompts x 6 formats = 270 runs. Snippet-level headline numbers: GPT-3.5-turbo GSM8K 76.6% (NL) → 49.3% (JSON-mode); LLaMA-3-8B Last-Letter 70.1% (NL) → 15.9% (XML); but classification tasks (DDXPlus, financial) *improved* under format restriction — [paper on ACL Anthology](https://aclanthology.org/2024.emnlp-industry.91/); [repo](https://github.com/appier-research/structure-gen)
- [INDEPENDENT, contested] The authors' own follow-up note (Dec 2024) concedes that prompt wording dominated: re-running with Outlines showed "prompt was the major improvement here", 1-shot CoT was worse than 0-shot in their hands, and "simply picking a single prompt or setting cannot be compared as both results can be noisy and bad." They keep the claim that stringent formats "may hinder reasoning-intensive tasks but enhance accuracy in classification tasks", and they note that adding schema restrictions such as `max_length` on a reasoning field materially changed results — [appier-research/structure-gen updates.md](https://github.com/appier-research/structure-gen/blob/main/updates.md); the rebuttal it answers is dottxt's "Say What You Mean" — [blog.dottxt.co](https://blog.dottxt.co/say-what-you-mean.html) (blocked; cited via the authors' reply) with notebooks at [dottxt-ai/demos](https://github.com/dottxt-ai/demos/tree/main/say-what-you-mean)
- [INDEPENDENT, snippet-level only] Later work claims a "structure snowballing"/"alignment tax" when constrained decoding is combined with reflection ("From Hallucination to Structure Snowballing", arXiv 2604.06066) and a "Structured Output Benchmark" of multi-source schemas (arXiv 2604.25359); full texts unreachable, numbers not verified — [arXiv 2604.06066](https://arxiv.org/abs/2604.06066); [arXiv 2604.25359](https://arxiv.org/abs/2604.25359)

### Inferences
- The failure classes that constrained decoding cannot fix are exactly the ones the RPG engine cares about: wrong-but-valid values (a Condition number that does not follow from the scene), truncation under `max_tokens` (a long `narrative` string inside JSON is the most likely truncation point), and refusals/tool-call-as-text leaks when thinking is off. A deterministic validator with retry is still required after schema-valid output.
- Length/pattern constraints must be enforced client-side on all three vendors; put the constraint text into the field description and re-validate with the full schema.
- Long free-text fields inside JSON (narrative prose) are the riskiest part of a mixed record: they cost escaping overhead (OpenAI notes JSON "can be more verbose, and require character escaping"), they are where truncation lands, and the Tam et al. dispute shows reasoning-in-JSON quality is highly prompt-sensitive. Keeping prose outside the JSON (or in a separate call) removes that risk.

### Gaps
- No independent, current (2025–2026) measured failure rate for schema-valid-but-semantically-wrong outputs on frontier models was retrievable; the JSONSchemaBench leaderboard (Google Sheet) and the arXiv "Structured Output Benchmark" were unreachable.
- No source quantified failure rates specifically for long strings, nested arrays or escaping inside constrained JSON on production APIs.

## KQ2. Does splitting "produce structured decision" then "write prose from it" improve mechanics/narration consistency?

### Takeaway
Vendors (Anthropic, OpenAI) recommend prompt chaining with programmatic gates between steps for exactly this shape of task, and Tam et al. tested a two-stage "NL-to-Format" variant; but I found no controlled study that measures mechanics-vs-narration consistency for a decide-then-narrate split. Evidence is architectural guidance plus indirect results, not a measured effect size.

### Cited Findings
- [VENDOR, Anthropic] "Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one"; programmatic "gates" check intermediate output; worked example: "Writing a document outline, validating it meets criteria, then drafting the full document based on that outline." Evaluator-optimizer loops are recommended "when clear evaluation criteria exist" and only "when it demonstrably improves outcomes" — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- [VENDOR, Anthropic] Long-context tip: ask Claude to quote/extract relevant facts into tags first, then act on them ("Place these in <quotes> tags. Then, based on these quotes, list all information..."), and "Queries at the end can improve response quality by up to 30 percent in tests" — [Anthropic, Prompting best practices, Long context prompting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)
- [VENDOR, Anthropic] "Use structured formats for state data: When tracking structured information (like test results or task status), use JSON or other structured formats to help Claude understand schema requirements" — [Anthropic, Prompting best practices, Long-horizon reasoning and state tracking](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-horizon-reasoning-and-state-tracking)
- [VENDOR, Anthropic] "Separate, fresh-context verifier subagents tend to outperform self-critique" (Fable 5 guidance) — [Anthropic, Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- [VENDOR, OpenAI] GPT-4.1: for non-reasoning use, "prompting the model to think step by step ... can be an effective way for a model to break down problems"; for GPT-5 minimal reasoning, "Prompting the model to give a brief explanation summarizing its thought process at the start of the final answer" helps — [GPT-4.1 guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt4-1_prompting_guide.ipynb); [GPT-5 guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5_prompting_guide.ipynb)
- [INDEPENDENT] Tam et al. included "NL-to-JSON: 2-stage" (answer in natural language, then convert to JSON with a second call) as one of six formats across 270 experiments; their authors' note reports classification tasks benefit from constrained answer spaces because JSON-mode "constrain[s] possible answers, thus reducing errors in answer selection" while "natural language responses may introduce distractions, leading to parsing errors" — [structure-gen updates.md](https://github.com/appier-research/structure-gen/blob/main/updates.md). (Snippet-level: the paper reports NL-to-Format recovers most of the reasoning loss; exact per-task numbers not verifiable here.)
- [INDEPENDENT] "LLMs Get Lost in Multi-Turn Conversation" (Laban et al., Microsoft, 2025; 15 models, 200k+ simulated conversations, six generation tasks): average 39% performance drop multi-turn vs single-turn, decomposed into "minor loss in aptitude" and "significant increase in unreliability"; models "make assumptions in early turns and prematurely attempt to generate final solutions, on which they overly rely" — [Microsoft Research page](https://www.microsoft.com/en-us/research/publication/llms-get-lost-in-multi-turn-conversation/); [repo](https://github.com/microsoft/lost_in_conversation)

### Inferences
- The engine's `advance` contract (structured `adjudication` + `operations` verified by code, narrative rendered separately) matches the vendor-recommended "gate between steps" pattern. The strongest supportable design is: (1) one call producing the structured adjudication (capabilities, outcome, operations) under strict schema; (2) deterministic validation of that record; (3) a second call (or second phase) writing prose *from* the validated record with the record in context and a validator checking that no numbers/tags leak. This gives a place for a validator to reject without discarding the prose, and avoids putting long prose inside the JSON.
- The multi-turn unreliability finding argues for re-supplying the full current state (the `context` output) every turn rather than relying on conversation memory, which the repository contract already does.

### Gaps
- No study found that measures "mechanics/narration consistency" (e.g., narrative contradicting a recorded stat change) for one-call vs two-call designs. This remains an unproven, though widely recommended, practice.
- Full text of Tam et al. and its NL-to-Format numbers could not be fetched.

## KQ3. Long system prompts / rule documents: length, position, reminders, checklists vs prose

### Takeaway
Independent work shows adherence degrades with instruction count and with context length (IFScale: best models ~68% at 500 simultaneous instructions; attention-dilution demo: 4.0/4 → 1.5/4 as input grows 500→8k tokens), with a primacy bias in most models. Vendors converge on: keep rule files short, section them with headers/XML, put long data at top and instructions/query at the end (Anthropic) or at both ends (OpenAI), and re-inject key reminders per turn via turn-scoped system messages rather than editing history.

### Cited Findings
- [INDEPENDENT, snippet-level] IFScale (Jaroslawicz et al., 2025): 500 keyword-inclusion instructions on a report-writing task, instruction density scaled 10→500, 20 models; "even the best frontier models only achieve 68% accuracy at the max density of 500 instructions"; three degradation shapes (threshold, linear, exponential) correlated with model size/reasoning; "a universal bias toward earlier instructions that peaks in the 150–200 range before collapsing into uniform failure"; distinct error categories (omission vs modification) — [arXiv 2507.11538](https://arxiv.org/abs/2507.11538); [Semantic Scholar entry](https://www.semanticscholar.org/paper/d7c206fcc98568f886d2fac3c49e8cc08e72a747)
- [INDEPENDENT, small demo] "Attention dilution": fixed ~300-token system prompt, user input padded with filler; adherence score 4.0/4 at ~500 tokens, 3.5/4 at ~2,000, 1.5/4 at ~8,000 (single model, temperature 0.7); reminders/repetition proposed but not tested — [yiheinchai/attention-dilution](https://github.com/yiheinchai/attention-dilution)
- [INDEPENDENT, snippet-level] "Prompt Design at Scale: How Format, Instruction Count, and Context Length Shape Instruction Adherence and Hallucination" (arXiv 2607.19257, 2026) reports the placement effect (system prompt vs user turn) is "real and larger in magnitude than format effect in four of five models tested"; full text unreachable, numbers unverified — [arXiv 2607.19257](https://arxiv.org/abs/2607.19257)
- [INDEPENDENT, snippet-level] Position-bias reviews summarize that most models show primacy (constraints at the start followed more reliably) while "Mixtral-8x-7b, Gemini and Claude models demonstrate a recency effect with higher compliance for constraints appearing later in the prompt"; the "30–50% loss for mid-prompt rules" figure circulates in practitioner posts without a traceable primary source — [TianPan, The Instruction Position Problem](https://tianpan.co/blog/2026/04/14/the-instruction-position-problem); [IntuitionLabs](https://intuitionlabs.ai/articles/llm-position-bias-primacy-recency-effects) (both blocked; treat as unverified)
- [INDEPENDENT, snippet-level] "Instruction Adherence in Coding Agent Configuration Files: A Factorial Study of Four File-Structure Variables" (arXiv 2605.10039) exists and is directly relevant (CLAUDE.md/AGENTS.md-style files); full text unreachable — [arXiv 2605.10039](https://arxiv.org/abs/2605.10039)
- [VENDOR, Anthropic/Claude Code] "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"; "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost"; "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out"; "The over-specified CLAUDE.md: If your CLAUDE.md is too long, Claude ignores half of it"; convert always-required actions to hooks because "CLAUDE.md instructions ... are advisory, hooks are deterministic" — [Claude Code, Best practices](https://code.claude.com/docs/en/best-practices)
- [VENDOR, Anthropic] "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" (context rot / attention budget); aim for "the smallest possible set of high-signal tokens"; organize the system prompt into sections (`<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description`) with XML or Markdown headers; prefer "diverse, canonical examples" over "a laundry list of edge cases"; find the "right altitude" between brittle hardcoded logic and vague guidance — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [VENDOR, Anthropic] "Provide instructions as sequential steps using numbered lists or bullet points when the order or completeness of steps matters"; examples: "Include 3–5 examples for best results", wrapped in `<example>` tags; "Put longform data at the top ... above your query, instructions, and examples" — [Anthropic, Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [VENDOR, Anthropic] Per-turn reminders: send them as turn-scoped system messages (`clear_at: "next_user_message"`, beta header `mid-conversation-system-clear-at-2026-08-21`), appended after tool results, leaving earlier copies in place; editing history "restarts the prompt cache" and invalidates thinking blocks. Precedence: "Later system messages override earlier ones"; mid-conversation system messages "take precedence over the top-level system field for the turns that follow them" — [Anthropic, Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1); [Anthropic, Mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)
- [VENDOR, Anthropic] For a long system prompt, "pair the instruction with a short reminder near the end of the prompt" (example `<tone_preference>Keep outputs reasonably concise.</tone_preference>`) — [Anthropic, Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [VENDOR, Anthropic] Fable 5 "sustains ... strong instruction retention across long, complex tasks"; "Instruction-following is improved enough that you can steer most behaviors with a brief instruction rather than enumerating each behavior by name"; "Skills developed for prior models are often too prescriptive for Claude Fable 5 and can degrade output quality" — [Anthropic, Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- [VENDOR, Anthropic] Opus 5: "its instruction following, tool calling, and reasoning stay consistent throughout the [1M-token] window" — [Anthropic, Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [VENDOR, OpenAI] GPT-4.1: "If you have long context in your prompt, ideally place your instructions at both the beginning and end of the provided context, as we found this to perform better than only above or below. If you'd prefer to only have your instructions once, then above the provided context works better than below." Delimiters: start with Markdown headers; XML "also perform[s] well"; JSON is "more verbose, and require[s] character escaping." Three short agentic reminders "increased our internal SWE-bench Verified score by close to 20%". "If there are conflicting instructions, GPT-4.1 tends to follow the one closer to the end of the prompt." "It's generally not necessary to use all-caps or other incentives like bribes or tips ... it could cause GPT-4.1 to pay attention to it too strictly." Recommended layout: Rules section with bullets, a more specific sub-section for a behaviour, "an ordered list" for workflow steps — [OpenAI Cookbook, GPT-4.1 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt4-1_prompting_guide.ipynb)
- [VENDOR, OpenAI] GPT-5: "poorly-constructed prompts containing contradictory or vague instructions can be more damaging to GPT-5 than to other models, as it expends reasoning tokens searching for a way to reconcile the contradictions"; a customer "removing them drastically streamlined and improved their GPT-5 performance" — [OpenAI Cookbook, GPT-5 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5_prompting_guide.ipynb)

### Inferences
- A rule set the size of this repository's AGENTS.md plus rules/narrative.md and rules/iron_engine.md is well inside the range where IFScale shows measurable omission; the primacy bias means rules late in a long document are most at risk, and Anthropic/OpenAI guidance is consistent with keeping only universally applicable rules in the always-loaded file and moving situational rules (travel, research, Condition) to on-demand documents, as AGENTS.md already prescribes.
- Because Claude models are reported (snippet-level) to weight later instructions more, and Anthropic documents "later system messages override earlier ones", the cheapest high-leverage mitigation is a short per-turn reminder of the 3–5 rules most often violated (template shape, no numbers in prose, record real `next_decision`), delivered as a turn-scoped system message or at the end of the user turn.
- Numbered steps are vendor-endorsed for ordered workflows; there is no independent evidence that numbering by itself improves adherence over prose for unordered constraints (the arXiv 2607.19257 abstract suggests format matters less than placement).

### Gaps
- No verified primary source for the "30–50% compliance loss for mid-prompt rules" claim.
- No independent measurement of whether repeated reminders help (attention-dilution author lists it as future work); vendor guidance is the only support.
- Full texts of IFScale, arXiv 2607.19257 and 2605.10039 were not retrievable; numbers above are from abstracts/snippets.

## KQ4. Negative instructions, "do not decide for the user", unrequested summaries/options/headings, and mitigations

### Takeaway
Vendors uniformly say positive framing and examples beat prohibitions (Anthropic: "Tell Claude what to do instead of what not to do"; positive examples "more effective than negative examples"); the one recurring HCI observation (Zamfirescu-Pereira et al. 2023) found non-experts overuse "do not" phrasing and it worked poorly; but I found no rigorous 2024–2026 controlled measurement of negative vs positive compliance rates, and one practitioner post claims the opposite for code review. Unrequested summaries, options menus and narration are documented model tendencies with vendor-supplied suppression prompts. Deterministic validators (hooks, Stop gates, verifier subagents) are the vendor-endorsed way to guarantee anything.

### Cited Findings
- [VENDOR, Anthropic] "Tell Claude what to do instead of what not to do. Instead of: 'Do not use markdown in your response' Try: 'Your response should be composed of smoothly flowing prose paragraphs.'"; "Use XML format indicators"; "Match your prompt style to the desired output style ... removing markdown from your prompt can reduce the volume of markdown in the output"; a long `<avoid_excessive_markdown_and_bullet_points>` block is supplied, but "Claude Fable 5.1 already formats less than earlier models, so on that model a block like this can suppress structure the content needs" — [Anthropic, Prompting best practices, Control the format of responses](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#control-the-format-of-responses)
- [VENDOR, Anthropic] "Positive examples showing how Claude can communicate with the appropriate level of concision tend to be more effective than negative examples or instructions that tell the model what not to do" (Sonnet 5); "Positive examples of the communication style you want tend to be more effective than instructions about what not to do" (Opus 5); "Instructions that call out thinking tags by name are less effective than the general form" (Opus 5) — [Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5); [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [VENDOR, Anthropic] Over-triggering: "Where you might have said 'CRITICAL: You MUST use this tool when...', you can use more normal prompting like 'Use this tool when...'"; "Instructions like 'If in doubt, use [tool]' will cause overtriggering" — [Anthropic, Prompting best practices, Tool use](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [VENDOR, Anthropic] Unrequested action / deciding for the user: Fable 5 "can occasionally take unrequested actions (drafting an email when none was asked for...)"; suggested rule: "When the user is describing a problem ... the deliverable is your assessment. Report your findings and stop. Don't apply a fix until they ask for one." Checkpointing rule: "Pause for the user only when the work genuinely requires them: a destructive or irreversible action, a real scope change, or input that only they can provide. If you hit one of these, ask and end the turn, rather than ending on a promise." Over-planning rule: "Do not ... narrate options you will not pursue in user-facing messages. If you are weighing a choice, give a recommendation, not an exhaustive survey." — [Anthropic, Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- [VENDOR, Anthropic] Opus 5 "can also expand the scope of a task, adding steps that weren't requested"; suggested rule "Deliver what was asked, at the scope intended ... stop short of actions that are clearly beyond what was asked"; written files "are often longer ... do not pad with filler sections, redundant summaries, or boilerplate"; correction narration can be limited with "Only correct an earlier statement when the error would change the user's code, conclusions, or decisions" — [Anthropic, Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [VENDOR, Anthropic] Preambles: prefill is gone on 4.6+; replacement is "Respond directly without preamble. Do not start with phrases like 'Here is...', 'Based on...', etc." plus "direct the model to output within XML tags, use structured outputs, or use tool calling. If the occasional preamble slips through, strip it in post-processing." Verbosity: newer models "May skip detailed summaries for efficiency unless prompted otherwise" — [Anthropic, Prompting best practices, Migrating away from prefilled responses](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#migrating-away-from-prefilled-responses)
- [VENDOR, Anthropic] Fable 5.1: "Earlier models overused bullets and bold in chat, and many prompts carry anti-formatting rules ... Claude Fable 5.1 leans the other way ... If your prompt contains anti-formatting language, remove it or replace it with a rule that says when specific formatting is appropriate"; recommended rule text: "Use lists and bullet points when asked to, or when the content is multifaceted enough that they help with clarity. If the person explicitly requests minimal formatting, always format your responses without bullet points, headers, lists, or bold emphasis, as requested. In conversational, personal, or emotional exchanges, keep to plain prose." — [Anthropic, Prompting Claude Fable 5.1, Formatting in chat](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#formatting-in-chat)
- [VENDOR, Anthropic] For a specific slip (unmarked quotation), "add one complete example of a correct response to the system prompt: the user's request, the response, and a sentence explaining why the response is correct" — [Anthropic, Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)
- [VENDOR, Anthropic] "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure"; make them relevant, diverse, and wrapped in `<example>` tags — [Anthropic, Prompting best practices, Use examples effectively](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#use-examples-effectively)
- [VENDOR, Anthropic] Deterministic enforcement: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens"; a Stop hook "runs your check as a script and blocks the turn from ending until it passes" (overridden after 8 consecutive blocks); "a verification subagent ... has a fresh model try to refute the result, so the agent doing the work isn't the one grading it"; "A reviewer prompted to find gaps will usually report some, even when the work is sound" — [Claude Code, Best practices](https://code.claude.com/docs/en/best-practices)
- [VENDOR, Anthropic] Self-verification: Opus 5 "verifies its own work without being told to ... Avoid instructing re-checks it already performs ('double-check your answer') ... these compound ... and add cost without improving results"; Fable 5: "Separate, fresh-context verifier subagents tend to outperform self-critique"; grounding prompt ("Before reporting progress, audit each claim against a tool result from this session...") "nearly eliminated fabricated status reports even on tasks designed to elicit them" in Anthropic's testing — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5); [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- [VENDOR, OpenAI] Cursor found GPT-5 "produced verbose outputs, often including status updates and post-task summaries that, while technically relevant, disrupted the natural flow of the user"; fix was the `verbosity` API parameter set low plus prompt-level overrides for code only; GPT-5 "by default ... does not format its final answers in Markdown" and a short positive rule ("Use Markdown only where semantically correct") induces it — [OpenAI Cookbook, GPT-5 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5_prompting_guide.ipynb)
- [VENDOR, OpenAI] "a single sentence firmly and unequivocally clarifying your desired behavior is almost always sufficient to steer the model on course"; "Add examples that demonstrate desired behavior; ensure that any important behavior demonstrated in your examples are also cited in your rules"; common failure mode: instructing "you must call a tool" can cause hallucinated inputs, so add "if you don't have enough information ... ask the user" — [OpenAI Cookbook, GPT-4.1 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt4-1_prompting_guide.ipynb)
- [INDEPENDENT] Intrinsic self-correction: Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (ICLR 2024) find that asking a model to review and revise its own answer without external feedback "often fails to improve and can degrade reasoning accuracy"; Kamoi et al. 2024 survey the narrow conditions under which it succeeds; a 2026 paper ("The Self-Correction Illusion", arXiv 2606.05976) reports models "confidently catch and repair errors in external content [but] routinely fail to identify identical errors in their own reasoning traces" (snippet-level) — [arXiv 2310.01798](https://arxiv.org/abs/2310.01798); [Kamoi et al. survey](https://arxiv.org/html/2406.01297v3); [arXiv 2606.05976](https://arxiv.org/html/2606.05976v1)
- [INDEPENDENT, HCI] "Why Johnny Can't Prompt" (CHI 2023) observed non-expert prompt writers favouring "Do not do X" phrasing which was "much less effective than 'Do thing Y' phrasing" (snippet-level; paywalled full text unreachable) — [ACM DL 10.1145/3544548.3581388](https://dl.acm.org/doi/fullHtml/10.1145/3544548.3581388)
- [PRACTITIONER, conflicting] A Substack case study claims negation-based prompts improved code-review bug detection by 39–89% on one task, while an engineering blog argues the "pink elephant" effect makes prohibitions unreliable; neither was retrievable in full and neither reports a controlled multi-model design — [Trilogy AI case study](https://trilogyai.substack.com/p/case-study-i-tested-the-negative); [16x.engineer, The Pink Elephant Problem](https://eval.16x.engineer/blog/the-pink-elephant-negative-instructions-llms-effectiveness-analysis)

### Inferences
- For template adherence (four-row summary, turn header, prose, optional Next), the vendor-endorsed stack is: one complete positive exemplar in the prompt, a short rule stating when structure is allowed, and a deterministic validator (the engine's renderer/validator or a Stop-style hook) that rejects extra headings, option menus or engine commentary and returns the specific violation for a retry. Self-critique passes without an external signal are not supported by the independent evidence and Anthropic says they add cost on Opus 5.
- "Do not choose the PC's action" is a scope rule; the vendor pattern that best fits is the Fable 5 checkpoint rule ("ask and end the turn, rather than ending on a promise"), phrased positively as what to deliver (the pending decision) rather than as a prohibition.
- On Fable 5.1 specifically, legacy anti-markdown blocks may now over-suppress structure the template needs (the four-row summary table); keep the template exemplar and drop generic anti-formatting language.

### Gaps
- No controlled, multi-model 2024–2026 measurement of negative vs positive instruction compliance was found; the claim rests on vendor guidance and one 2023 HCI observation.
- No study specifically on models adding unrequested "options menus" or headings in narrative/RPG settings.

## KQ5. Prose style control (purple prose, em dashes, "AI-sounding" text) and whether style rules measurably change output

### Takeaway
Corpus studies confirm em-dash frequency rose with LLM adoption (medRxiv odds ratio ~2.9), and vendors now treat style as promptable (Anthropic ships an anti-"mannered prose" instruction for Fable 5.1; OpenAI's CEO said in Nov 2025 that a no-em-dash custom instruction "finally" works), but I found no independent controlled study measuring how much a style rule shifts prose features, and one 2026 measurement claims the human-vs-AI dash gap is "much smaller and noisier than the common perception".

### Cited Findings
- [VENDOR, Anthropic] Fable 5.1 "writing is generally a step up ... with fewer stock phrases and less unexplained jargon", but "its prose is denser ... sentences run longer and there are fewer paragraph breaks. An instruction that defines the anti-pattern, mannered prose, helps." Supplied text: "Mannered prose substitutes metaphor and flourish for direct statement. Instead of 'a parameter worth varying,' the mannered writer produces 'a dial worth turning.' ... The fix is to say what you mean. When a literal phrase is available, use it." followed by "Please remove all mannered prose." (put in the user message, preferred, or system prompt) — [Anthropic, Prompting Claude Fable 5.1, Writing density](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#writing-density)
- [VENDOR, Anthropic] Readability in long agentic runs: "Don't use arrow chains, hyphen-stacked compounds, or labels you made up earlier ... Write complete sentences. Spell out terms." and "The way to keep output short is to be selective about what you include ... not to compress the writing into fragments, abbreviations, arrow chains" — [Anthropic, Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- [VENDOR, Anthropic] Sonnet 5: "prose style on long-form writing may shift. If your product relies on a specific voice, re-evaluate style prompts against the new baseline"; sampling parameters (`temperature`, `top_p`, `top_k`) return 400 on Sonnet 5, so "use system-prompt instructions to guide tone and variety instead"; generic negative aesthetic instructions ("don't use that color") "tend to shift the model to a different fixed palette rather than producing variety", whereas concrete specs or asking for options first work — [Anthropic, Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- [VENDOR, Anthropic] Style-by-imitation: "The formatting style used in your prompt may influence Claude's response style ... try matching your prompt style to your desired output style as closely as possible" — [Anthropic, Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#control-the-format-of-responses)
- [INDEPENDENT, snippet-level] medRxiv preprint corpus study: em-dash presence in abstracts rose with LLM adoption, odds ratio 2.92 (Discussion sections OR 2.96); em-dash use reached 20.3% of preprints by 2025 while declared generative-AI use rose to 3.6% — [arXiv 2606.29540](https://arxiv.org/abs/2606.29540)
- [INDEPENDENT, snippet-level] A 2026 measurement over 700,000+ words found a real but "much smaller and noisier" human-vs-AI dash-density gap than popular belief — [SlopDetector](https://slopdetector.org/blog/em-dash-ai-tell-data) (blocked; unverified)
- [INDEPENDENT, snippet-level] "Everyone prefers human writers, including AI" (arXiv 2510.08831) reports human and LLM judges prefer human-written prose in blind comparisons — [arXiv 2510.08831](https://arxiv.org/abs/2510.08831) (full text unreachable)
- [PRACTITIONER, snippet-level] Sam Altman (Nov 2025) said that telling ChatGPT not to use em dashes in custom instructions "finally does what it's supposed to do", implying earlier non-compliance with that negative style rule — reported via [Plagiarism Today](https://www.plagiarismtoday.com/2025/06/26/em-dashes-hyphens-and-spotting-ai-writing/) and [The Ringer](https://www.theringer.com/2025/08/20/pop-culture/em-dash-use-ai-artificial-intelligence-chatgpt-google-gemini) (both blocked; unverified)

### Inferences
- The most defensible style-control stack is (1) a short definitional anti-pattern paragraph (Anthropic's mannered-prose text is a vendor-tested template), (2) one canonical exemplar turn in the target voice, (3) a deterministic post-check for banned surface features (em dashes, "not X but Y", closing summaries, "Let me know if") with a targeted rewrite request. Sampling parameters are no longer a lever on Sonnet 5.
- Because style prompts are model-version sensitive (Anthropic explicitly says to re-evaluate them per model), any style rules in rules/narrative.md should be re-tested when the model changes rather than accumulated.

### Gaps
- No independent, quantitative study measuring the effect size of a style rule ("no em dashes", "no purple prose") on the target features across models; Anthropic's Fable 5.1 claim is qualitative.
- Wikipedia's "Signs of AI writing" catalogue (widely used as a checklist) could not be fetched from this environment.

## KQ6. Evaluation methods for template adherence and prose quality

### Takeaway
Template adherence is best measured with verifiable, programmatic checks in the IFEval tradition (regex/parsers on required sections, forbidden tokens, length); prose quality has no reliable automatic metric, LLM-as-judge is usable only with a rubric and held-out human checks, and a fresh-context reviewer beats self-grading. Vendors stress evaluating prompt changes against a held-out eval before shipping.

### Cited Findings
- [INDEPENDENT] IFEval (Zhou et al., 2023): "verifiable instructions" checked by code (word counts, keyword occurrence, format), 25 instruction types, 541 prompts; the reference implementation takes `{prompt, response}` JSONL and scores by rule — [google-research/instruction_following_eval](https://github.com/google-research/google-research/tree/master/instruction_following_eval); [arXiv 2311.07911](https://arxiv.org/abs/2311.07911)
- [INDEPENDENT, snippet-level] Successor benchmarks extend this to multi-constraint and judge-based settings: CFBench, WildIFEval, M-IFEval (NAACL 2025 Findings), MCJudgeBench (constraint-level judge evaluation, arXiv 2605.03858), "Deconstructing Instruction-Following" (arXiv 2601.18554), and multi-turn "One Battle After Another" (arXiv 2511.03508); a 2026 study finds built-in thinking shifts which constraint types fail ("When Built-in Thinking Helps and Hurts", arXiv 2606.09662) — [M-IFEval](https://aclanthology.org/2025.findings-naacl.344/); [arXiv 2605.03858](https://arxiv.org/abs/2605.03858); [arXiv 2601.18554](https://arxiv.org/abs/2601.18554); [arXiv 2511.03508](https://arxiv.org/abs/2511.03508); [arXiv 2606.09662](https://arxiv.org/abs/2606.09662) (all full texts unreachable)
- [INDEPENDENT] Multi-turn evaluation methodology: Laban et al. simulate "sharded" instructions delivered over turns and measure aptitude vs unreliability separately across 15 models and seven task types (code, database, actions, math, data2text, summary, translation) — [microsoft/lost_in_conversation](https://github.com/microsoft/lost_in_conversation)
- [VENDOR, Anthropic] "Give Claude a check it can run ... a script that diffs output against a fixture"; evidence over assertion: "Have Claude show evidence rather than asserting success"; "test changes by observing whether Claude's behavior actually shifts" when editing rule files — [Claude Code, Best practices](https://code.claude.com/docs/en/best-practices)
- [VENDOR, Anthropic] Tool-description iteration measurably changed outcomes ("Claude Sonnet 3.5 achieved state-of-the-art performance on the SWE-bench Verified evaluation after we made precise refinements to tool descriptions"); use "held-out test sets to prevent overfitting"; namespacing choice "ha[s] non-trivial effects on our tool-use evaluations" — [Anthropic, Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [VENDOR, Anthropic] Two-pass evaluation for review-type tasks: have the first pass maximise coverage ("Do not filter for importance or confidence at this stage - a separate verification step will do that ... include your confidence level and an estimated severity so a downstream filter can rank them") and "Iterate on prompts against a subset of your evals ... to validate recall or F1 score gains" — [Anthropic, Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- [VENDOR, Anthropic] "As always, measure the effect of any prompting changes on performance"; Skill/eval tooling: the skill-creator workflow includes running evals and "benchmark skill performance with variance analysis" — [Anthropic, Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- [VENDOR, OpenAI] Evaluate prompts with a held-out set; the GPT-5 guide points to a prompt-optimizer tool for detecting contradictory instructions — [OpenAI Cookbook, GPT-5 Prompting Guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5_prompting_guide.ipynb)

### Inferences
- For this repository, an IFEval-style harness is straightforward: a fixture set of `advance` inputs and a scorer that checks (a) JSON validity and schema, (b) rendered page matches templates/turn-output.md (exactly one four-row summary, one turn header, no extra `#` headings, no "ledger"/"assessment"/hash strings, no capability numbers in prose), (c) `next_decision` present when the scene ends on a choice, (d) forbidden style tokens. Prose quality would need a rubric-based judge in a fresh context with periodic human spot checks; the independent literature warns against trusting a model to grade its own turn.

### Gaps
- No published benchmark specifically for interactive-fiction/RPG turn templates was found.
- LLM-as-judge reliability for *style* (as opposed to correctness) is only snippet-level here (MCJudgeBench, "Everyone prefers human writers"); no verified numbers.
