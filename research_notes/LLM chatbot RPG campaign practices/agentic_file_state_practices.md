## KQ1. What can an agentic chat session do that a plain chatbot cannot (execute code, persist files, read repo instruction files, commit/push)? Vendor claims.

### Takeaway
Vendor documentation for Claude Code (and, more thinly for this session, Codex and Cursor) confirms the four capabilities the repository contract assumes: the agent reads and edits files, runs arbitrary shell commands including Python and git, loads a fixed instruction file (CLAUDE.md/AGENTS.md) at every session start, and can commit and push. Vendors are equally explicit that instruction files are advisory context, not enforced configuration, and that each session begins with an empty context window.

### Cited Findings
- Claude Code is positioned against chatbots: "Unlike a chatbot that answers questions and waits, Claude Code can read your files, run commands, make changes, and autonomously work through problems while you watch, redirect, or step away entirely." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Tool categories the vendor lists: file operations (read/edit/create), search, execution ("Run shell commands, start servers, run tests, use git"), web, code intelligence. "Without tools, Claude can only respond with text." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Access on launch: "Your terminal. Any command you could run: build tools, git, package managers, system utilities, scripts. If you can do it from the command line, Claude can too." and "Your git state. Current branch, uncommitted changes, and recent commit history." It "commits the changes if you ask." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Instruction file loading: "CLAUDE.md files ... You write these files in plain text; Claude reads them at the start of every session." Files "in the directory hierarchy above the working directory are loaded at launch. Files in subdirectories load on demand when Claude reads files in those directories." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- AGENTS.md support (Claude Code v2.1.277+): "Claude Code can read AGENTS.md as your project instructions, so a repository already set up for other coding agents works without adding a CLAUDE.md." By default it reads AGENTS.md only when no CLAUDE.md/CLAUDE.local.md exists in the working directory or above; a `claude-md-and-agents-md` setting loads both. A CLAUDE.md that merely "tells Claude in words to read AGENTS.md" is unreliable: "Claude sees AGENTS.md only if it decides to open the file." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Explicit vendor statement that instructions are not enforcement: "Both are loaded at the start of every conversation. Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Session persistence model: "Sessions are independent. Each new session starts with a fresh context window, without the conversation history from previous sessions." Conversations are saved locally as JSONL under `~/.claude/projects/`; `--continue`/`--resume` reopen the same session ID. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Auto memory (vendor-written notes) loads only "the first 200 lines or 25KB of MEMORY.md, whichever comes first." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Cloud sessions: "each session runs in an isolated, Anthropic-managed VM"; "git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials"; sessions "need access to your GitHub repositories to clone code and push branches." — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Non-interactive/headless mode exists (`claude -p`, `--allowedTools`, `--output-format json`) for CI, pre-commit hooks and scripted fan-out. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Codex (snippet only; developers.openai.com blocked): Codex discovers instruction files per directory in the order `AGENTS.override.md, AGENTS.md, TEAM_GUIDE.md, .agents.md` and "stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)." — [OpenAI Codex AGENTS.md guide](https://developers.openai.com/codex/guides/agents-md) via search snippet; the 32 KiB constant is corroborated by a GitHub issue quoting `src/config/mod.rs`: "Larger files are *silently truncated* to this size" — [openai/codex issue #7138](https://github.com/openai/codex/issues/7138)
- Cursor (snippet only; cursor.com blocked): Cursor rules docs say to keep rules "under 500 lines and split large rules into multiple, composable rules"; the Cursor CLI "also reads AGENTS.md and CLAUDE.md at the project root (if present) and applies them as rules alongside .cursor/rules." — [Cursor Rules docs](https://cursor.com/docs/rules) and [Cursor CLI docs](https://cursor.com/docs/cli/using) via search snippets
- AGENTS.md convention: "a simple, open format for guiding coding agents ... a dedicated, predictable place to provide context and instructions." The GitHub repo shows 24.6k stars / 1.9k forks at fetch time. — [agentsmd/agents.md on GitHub](https://github.com/agentsmd/agents.md)

### Inferences
- The repository contract's assumption that "the model reads AGENTS.md each session" is vendor-supported for Claude Code, Codex and Cursor, but the *mechanism* differs (Claude Code loads it at launch and shows a "AGENTS.md loaded" line; Codex has a 32 KiB combined cap with silent truncation; Cursor treats it as a rule). A project instruction file should therefore stay well under 32 KiB and not rely on being read in full by every tool.
- "Commit and push" is a shell capability, not a dedicated tool; whether it happens depends on permission mode and, in cloud sessions, on the proxy having push access. Verification of publication (as the AGENTS.md contract demands) must be an explicit command (`git log origin/...`, `git status`), not an assumption.

### Gaps
- Could not fetch OpenAI's Codex docs pages (sandbox modes, approval policies, AGENTS.md precedence) or Cursor's rules page directly; the GitHub mirror of `openai/codex/docs/*` only links out to developers.openai.com. Gemini CLI (GEMINI.md) and ChatGPT code interpreter were not covered at all.

## KQ2. Documented failure modes (claiming to have run commands, hand-editing generated files, skipping validation, instruction drift in long sessions, sycophancy) and recommended mitigations

### Takeaway
Vendors document context-driven instruction loss, premature "done" declarations, and "trust-then-verify" gaps, and they recommend deterministic gates (hooks, tests, exit codes, Stop hooks) precisely because instruction files are advisory. Independent evidence for tool-result fabrication and mid-session rule decay exists but, in this session, was reachable mainly through snippets and a closed GitHub issue; it should be cited with that caveat.

### Cited Findings
- Vendor-acknowledged context degradation: "LLM performance degrades as context fills. When the context window is getting full, Claude may start 'forgetting' earlier instructions or making more mistakes." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Compaction loses early instructions: "Claude compacts automatically, but instructions from early in the conversation can get lost. Put persistent rules in CLAUDE.md." When context fills, "It clears older tool outputs first, then summarizes the conversation if needed ... detailed instructions from early in the conversation may be lost." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Premature completion: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Mitigation: "Give Claude something that produces a pass or fail ... a test suite, a build exit code, a linter, a script that diffs output against a fixture." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "The trust-then-verify gap. Claude produces a plausible-looking implementation that doesn't handle edge cases. Fix: Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Evidence over assertion: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Deterministic gates: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." A Stop hook "runs your check as a script and blocks the turn from ending until it passes. Claude Code overrides the hook and ends the turn after 8 consecutive blocks." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Hook semantics: PreToolUse "Can block it"; exit code 2 "blocks whether or not you print JSON: even a JSON permissionDecision of 'allow' can't override it." Hook events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop, SessionEnd, FileChanged. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Long-running-agent failure modes observed by Anthropic: agents "declare the job done" prematurely, mark features complete "without proper testing," and try to "one-shot the app." Their harness forbids editing tests: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic's design principle for grounding: "it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress." Also "Poka-yoke" tool design: "change the arguments so that it is harder to make mistakes." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Tool output design: tools "should take care to return only high signal information"; error responses should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks"; semantically meaningful identifiers instead of "arbitrary alphanumeric UUIDs ... significantly improves Claude's precision." — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Mid-session rule decay (user report, not vendor-confirmed): GitHub issue #80873 (opened 2026-07-24, closed "not planned", label stale) states "Claude Code applies CLAUDE.md rules correctly at the start of a session, then progressively ignores them as the conversation grows — even when the rules remain in context," by turn 20 rules are "effectively gone," and "Rules under 200 lines still fade." It links nine similar issues. Suggested mitigations: re-inject violated rules, rule pinning, "Post-response audit hook — Run validation after model response; force retry if violations detected," adherence telemetry. No maintainer response recorded. — [anthropics/claude-code issue #80873](https://github.com/anthropics/claude-code/issues/80873)
- Vendor's own rule-loss statement: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Tool-use hallucination / imagined command output (snippet only; primary pages blocked): a search summary attributes to the EnIGMA paper (ICML 2025) a failure mode where "agents stop actually running commands and start imagining the output instead," building "on the imaginary result" in "a self-referential loop." The same summary cites an "11.6%" accuracy figure for self-diagnosing tool-use hallucinations. Both come from a Medium post and could not be verified against the paper. — [Medium: Tool-Use Hallucination (unverified)](https://medium.com/@yaseenmd/tool-use-hallucination-the-hidden-ai-reliability-gap-breaking-your-automation-2fe7d1c1af1a); related benchmark listing: [AgentProp-Bench, arXiv 2604.16706 (title only)](https://arxiv.org/pdf/2604.16706)
- Sycophancy in coding agents (snippet only): a search summary describes the mechanism as "the answer changes when the user states a belief confidently, even though the retrieved evidence, system policy, and tool results did not change," with the example "A developer agent accepts a mistaken API assumption and then edits code around the wrong contract." — [FutureAGI sycophancy glossary (snippet)](https://futureagi.com/glossary/sycophancy/); a 2026 preprint titled "Agents Don't Just Agree, They Remember: Benchmarking Persistent Sycophancy in Stateful Personal Agents" exists but was not readable here — [arXiv 2607.10526 (title only)](https://arxiv.org/html/2607.10526)
- Small-model tool-call drift (project README, independent): "Models below ~70B parameters degrade after 4–5 sequential tool calls, drifting from their instructions toward the most recently read content." — [open-tabletop-gm README](https://github.com/thecosine/open-tabletop-gm)
- Reviewer bias: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- The failure modes in the objective map onto documented ones: "claiming to have run a command" = tool-use hallucination (independent literature, unverified here); "editing generated files by hand" is not named in vendor docs but is exactly what a PreToolUse hook denying writes to `play/` or generated sheets would catch; "skipping validation" = the vendor's "trust-then-verify gap"; "drifting from instructions" = context-fill degradation plus the user-reported decay; sycophancy is treated in the literature as a distinct failure.
- For a campaign engine, the strongest vendor-endorsed mitigations are: (1) commands that return pass/fail and carry evidence (hash, turn number, accepted-event ID) in structured output; (2) hooks that block hand edits of generated paths and block ending a turn until validation passes; (3) demanding evidence ("the command it ran and what it returned") rather than narrative claims; (4) a fresh-context reviewer for tenth-turn evidence reviews, with instructions to report only correctness gaps.

### Gaps
- No primary-source verification of the EnIGMA "imagined output" description or of the 11.6% figure; the arXiv host was blocked.
- No quantitative independent study located specifically on "editing generated files by hand" as a failure category.
- No maintainer or vendor confirmation of the mid-session decay in issue #80873 beyond the vendor's general "performance degrades as context fills" statement.

## KQ3. Practitioner patterns for durable memory (append-only logs, event sourcing, snapshots, IDs, short instruction files, progressive disclosure) and evidence on instruction-file length vs adherence

### Takeaway
Vendor guidance converges on short, specific instruction files plus on-demand loading (skills, path-scoped rules, "just-in-time" references) and external structured notes; independent 2025-2026 work on agent memory increasingly adopts event sourcing (append-only log as truth, deterministic projections, hand edits forbidden). Evidence on length vs adherence is mixed: the vendor states a 200-line target, while a 2026 preprint (reachable only via snippets) reportedly found no measurable effect of length/position/contradiction across 1,650 sessions, though having a file at all mattered enormously.

### Cited Findings
- Vendor length target: "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Also "Specificity: write instructions that are concrete enough to verify" and "Consistency: if two rules contradict each other, Claude may pick one arbitrarily." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- What belongs in the always-loaded file: "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Pruning heuristic: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" and "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Progressive disclosure mechanisms: `@path` imports (still loaded at launch, depth 4), `.claude/rules/` with `paths` frontmatter that "only load into context when Claude works with matching files," and skills that load "only when you invoke them or when Claude determines they're relevant." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Context engineering principles: agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime"; "context rot": "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; structured note-taking (NOTES.md) lets an agent keep "precise tallies across thousands of game steps." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Long-running harness pattern: initializer creates `init.sh`, `claude-progress.txt`, feature list JSON with everything "initially marked as failing," and an initial git commit; "Git commits with descriptive messages combined with progress file updates allow the model to use git to revert bad code changes and recover working states." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Compaction instructions can be pinned: "Customize compaction behavior in CLAUDE.md with instructions like 'When compacting, always preserve the full list of modified files and any test commands'." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Independent adherence study (snippet only; arXiv blocked): "Instruction Adherence in Coding Agent Configuration Files" (arXiv 2605.10039) reportedly "ran 1,650 Claude Code sessions, changing the file's length, where the rule sat in it, how the files were arranged, and whether the file contradicted itself. None of it made a measurable difference," while "With no file at all, Claude followed the rule 0 times out of 524, against 67.7% with one." — [arXiv 2605.10039 (title/abstract via search)](https://arxiv.org/pdf/2605.10039), summarized by [alexdunlop.com (snippet)](https://www.alexdunlop.com/writing/claude-md-best-practices) and [futureagi.com (snippet)](https://futureagi.com/blog/claude-md-instruction-governance/). Contradicts the vendor's length-reduces-adherence claim above; the disagreement is noted rather than resolved.
- Event sourcing for agents (independent, GitHub README readable): Conversation ESAA captures turns via hooks into "an append-only activity.jsonl" and "deterministically project[s] read models such as handoff.md, state.md, decisions.md, and tasks.json"; "activity.jsonl serves as the single source of truth"; rule: "Do not edit the projections by hand; all writing passes through the CLI"; it ships `verify`, `doctor`, `repair` commands and `update`/`repair` "refuse to overwrite modified files unless invoked with --force." — [elzobrito/conversation-esaa](https://github.com/elzobrito/conversation-esaa); paper: [ESAA-Conversational, arXiv 2606.23752 (abstract via search)](https://arxiv.org/abs/2606.23752)
- The ESAA paper's stated boundary (snippet): "mechanical capture is automatic; curation is judgment; reading is selective; and the complete log remains available without being ingested wholesale by every new agent." — [arXiv 2606.23752 (snippet)](https://arxiv.org/html/2606.23752)
- Other 2026 event-sourcing work (titles/abstract snippets only): "The Log is the Agent: Event-Sourced Reactive Graphs for Auditable, Forkable Agentic Systems" describes "The append-only event log serves as the source of truth, with the working graph as a deterministic projection of that log" — [arXiv 2605.21997](https://arxiv.org/html/2605.21997); OpenHands SDK "treating all interactions as immutable events appended to a log," reporting "0.20 ms median per-event persistence, 4.1 ms full state replay and 380 KB median storage per conversation" — [arXiv 2511.03690 (snippet)](https://arxiv.org/pdf/2511.03690); PROJECTMEM "A Local-First, Event-Sourced Memory and Judgment Layer for AI Coding Agents" — [arXiv 2606.12329 (title only)](https://arxiv.org/pdf/2606.12329)
- Codex instruction-file cap: silent truncation at 32 KiB combined; reporter's 40 KB AGENTS.md was truncated without notice (issue closed not planned, Nov 2025). — [openai/codex issue #7138](https://github.com/openai/codex/issues/7138)
- Cursor (snippet): "Good Cursor rules should be kept under 500 lines"; advice to "reference files instead of copying their contents." — [Cursor Rules docs (snippet)](https://cursor.com/docs/rules)

### Inferences
- The repository contract's structure (short AGENTS.md; `rules/*.md` and `docs/*.md` loaded on demand; `context`/`record ID`/`history --turn N` commands as lightweight identifiers) matches both Anthropic's "just-in-time" context guidance and the ESAA "reading is selective" boundary.
- The most defensible position on length is: existence of the file dominates; length beyond a few hundred lines costs context and, per vendor, some adherence, but structural tweaks alone will not fix mid-session drift. Deterministic checks (hooks, validators) should carry the invariants that matter.
- An append-only event log with deterministic projections is now a recognized pattern in both practitioner tooling (ESAA) and academic writing (2605.21997, 2511.03690); the campaign design's hash chain adds tamper-evidence that none of the found sources describe explicitly.

### Gaps
- The 1,650-session study's method and exact numbers could not be verified against the paper (arXiv blocked). Its "67.7%" and "0/524" figures come from third-party summaries.
- No source found that measures adherence specifically as a function of instruction-file length in Codex or Cursor.
- No source found describing hash chains over agent event logs; "The Log is the Agent" mentions auditability but its hashing details were unreadable.

## KQ4. How a fresh session should resume reliably (what to load first, how much, verifying head state)

### Takeaway
Vendor and practitioner sources agree on a sequence: read a small hand-off/progress file and recent git log first, run a cheap health check to confirm the working state is not broken, then pull details on demand; never rely on prior conversation, and treat auto-compaction and VM reclamation as things that can drop in-flight work.

### Cited Findings
- Anthropic's harness: before new work, agents should "read the git logs and progress files to get up to speed" and run basic end-to-end tests to "quickly identify if the app had been left in a broken state." Sessions are "like engineers working in shifts, where each new engineer arrives with no memory of what happened on the previous shift." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- ESAA resume protocol: "Read first `.conversation-esaa/handoff.md`" to identify current goals; consult `state.md`, `topics.md`, `decisions.md`, `tasks.json` "only for gaps"; use `context --last 20` if contradictions remain. — [elzobrito/conversation-esaa](https://github.com/elzobrito/conversation-esaa)
- Claude Code loads at launch: CLAUDE.md/AGENTS.md from cwd and ancestors, user rules, auto memory (first 200 lines/25 KB), skill descriptions only; subdirectory instruction files load when files there are read. `/context` shows what loaded. — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Checkpoints are not git: "Checkpoints only track changes made through Claude's file editing tools. Changes made through Bash commands or external processes are not captured. This isn't a replacement for git." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Cloud sessions lose in-flight work: "Cloud sessions stop after a period of inactivity and the session's VM is reclaimed ... Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored." Cloud VM "clones your current directory's GitHub remote at your current branch, not your local checkout, so push first if you have local commits." — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Fresh session with a written spec beats a long one: "Once the spec is complete, start a fresh session to execute it. The new session has clean context focused entirely on implementation"; "A clean session with a better prompt almost always outperforms a long session with accumulated corrections." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Session-start hooks can inject state: `SessionStart` fires "When a session begins or resumes"; hook stdout on exit 0 is read by Claude Code. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Game-master harness resume (independent): Claude-Code-Game-Master loads "the full campaign state from disk before Claude generates a response" and every turn receives "previously-on summary, open threads, NPC voices, active clocks, pending consequences"; "The model never searches for what it needs; the harness 'puts it on the table.'" Rule: "persist before you narrate — every change saved first." — [Sstobo/Claude-Code-Game-Master](https://github.com/Sstobo/Claude-Code-Game-Master)
- open-tabletop-gm loads its SKILL.md only on `/gm load <name>` "to keep the standing system prompt lean—approximately 2,300 tokens." — [thecosine/open-tabletop-gm](https://github.com/thecosine/open-tabletop-gm)

### Inferences
- A reliable resume for the campaign engine is: (1) instruction file auto-loaded; (2) one command (`context`) that validates the full event chain internally and prints head hash, turn, pending decision and active obligations; (3) `git status`/`git log origin` to confirm published head equals local head before any new turn; (4) on-demand `record ID`/`history --turn N`. This is the same shape as ESAA's handoff.md-first protocol and Anthropic's "git log + progress file + smoke test."
- Because compaction can drop early instructions and cloud VMs can be reclaimed mid-command, the engine's requirement to submit "the actual current hash, turn and a unique request ID" and to treat exact retries as idempotent is well-motivated: it makes a resumed or compacted session re-derive rather than remember.
- A SessionStart hook that prints `context` output would make head-state verification automatic rather than instruction-dependent; a PreToolUse hook denying edits to generated paths converts a prose rule into a deterministic gate.

### Gaps
- No vendor documentation found on how much context to load at resume in tokens; only the auto-memory cap (200 lines/25 KB) and Codex's 32 KiB instruction cap are quantified.

## KQ5. Existing open-source LLM tabletop RPG / interactive-fiction campaign projects with file-backed agent state, and lessons

### Takeaway
Several 2025-2026 GitHub projects run campaigns from files inside coding-agent harnesses. The recurring lessons are: mechanics in code, narration in the model; persist before narrating; keep the resident prompt small and load modules on demand; retrieval is not truth; and return explicit "unresolved/ruling required" results instead of inventing outcomes. None found uses a hash chain or Git-commit-per-turn as the authoritative store.

### Cited Findings
- Claude-Code-Game-Master (Claude Code harness): state is "plain JSON per campaign" under `world-state/campaigns/<name>/`; "persist before you narrate — every change saved first"; "Memory is bounded by your filesystem, not the token limit"; "A single mega-prompt can fake a GM for one session. It can't remember your campaign next week, it can't enforce its own rules." Architecture: "Lean router core," on-demand skills (`gm-combat`, `gm-spellcasting`, `gm-social`), Bash wrappers (`gm-campaign.sh`, `gm-combat.sh`) calling Python managers, optional D&D 5e API "to ground numbers in official rules instead of guessing," docs with "staleness-checking against source code." — [Sstobo/Claude-Code-Game-Master](https://github.com/Sstobo/Claude-Code-Game-Master)
- open-tabletop-gm (OpenCode/LM Studio/any LLM): "offloads everything mechanical to Python so the LLM can focus on narration and judgment"; campaigns are plain Markdown (`state.md / world.md / npcs.md / session-log.md / characters/`) outside the repo under `$GM_CAMPAIGN_ROOT`; typed-edge relationship graph with "source anchors" and `/gm graph scene-context` to avoid re-reading NPC files "when context compaction forces file exclusion"; local models "<~70B ... degrade after 4–5 sequential tool calls." — [thecosine/open-tabletop-gm](https://github.com/thecosine/open-tabletop-gm)
- gamemaster (SingularityNET Omega runtime): SQLite store with "campaigns, entities, facts, documents, relationships, sessions, rulings, retrieval records, and append-only event history"; "State changes and their event records are applied in one transaction during the tested turn flow"; capability-based actions; when mechanics cannot be resolved the system returns `UNSUPPORTED`, `UNRESOLVED`, or `RULING_REQUIRED` rather than inventing results; "Retrieval is never campaign truth. A retrieved campaign chunk is still a search result"; "Treat every ingested document as untrusted text"; self-described as "a working first draft ... not a finished game-master product." — [spencerthayer/gamemaster](https://github.com/spencerthayer/gamemaster)
- VirtualGameMaster (snippet): configurable "maximum number of messages in chat history before creating an updated game state and the number of recent messages to keep after updating the game state" (periodic snapshotting of state from chat). — [Maximilian-Winter/VirtualGameMaster](https://github.com/Maximilian-Winter/VirtualGameMaster)
- dnd-llm-game (snippet): local Ollama DM that "owns the dice and combat rules, and remembers your campaigns between sessions." — [tegridydev/dnd-llm-game](https://github.com/tegridydev/dnd-llm-game)
- Anthropic's own long-horizon game example: Claude playing Pokémon keeps external notes and "maintains precise tallies across thousands of game steps." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- The dice-roller repository's design is stricter than every project found: those projects persist state in JSON/Markdown/SQLite that the model or scripts may rewrite, whereas an append-only event with full state, a hash chain, code-regenerated reading pages, and Git publication per turn adds tamper evidence and reproducibility. gamemaster's single-transaction "state change + event record" and its refusal codes are the closest analogues to `advance` with justified operations and "code checks required evidence, not its truth."
- Lessons transferable to the campaign contract: keep the resident instruction file small and put procedures in on-demand rules/skills (all three projects); generate scene context by command rather than have the model hunt for it (Claude-Code-Game-Master); treat book references and retrieval as untrusted, non-canonical input (gamemaster), which matches "Research does not grant PC knowledge."

### Gaps
- None of the located projects publishes post-mortems with quantitative reliability data (e.g., how often the model edited state files by hand or skipped a save); lessons are README claims by the authors.
- No interactive-fiction (non-RPG) project with git-backed agent state was found in the searches run.
